# Campsite R5.8 — 세션 3: Core + Contracts + Integration (계약 오너)

문서 버전: R5.8-S3 · 2026-10-10  
소유 폴더: **`packages/contracts/**`, `services/core/**`, `ops/**` 및 모노레포 공용 설정 파일**(`package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `.gitignore`, `.github/workflows/**`, 루트 README 등).  
`apps/web/**`와 `services/runner/**`는 **읽기 전용**이다. 세션 1·2의 작업을 대신 수정하지 않는다.

## 역할과 목표

**세 세션을 연결하는 정본 계약(API·타입·fixture)을 가장 먼저 확정**하고, Cloudflare Workers + D1 + R2 기반 Core를 구현한다. Google 로그인 → Workspace·Plan 논리 배정 → 채널 생성 → Run 큐잉 → VPS Runner의 outbound claim → Vista 원자적 게시 → For Me Feed → 별도 Origin의 안전한 재생까지 작동시킨다.

기본 원칙: **사용자가 구독하는 것은 VM이나 파일 저장 공간이 아니라, AI가 생산한 정보를 더 편하게 소비하는 경험이다.** Core는 사용자에게 노출되는 기술 메뉴가 아니라 이 경험의 신뢰 가능한 운영 계층이다.

**핵심 순서: ① 루트 뼈대·contracts·fixture의 첫 커밋 → ② 인증·DB·stub Runner G1 → ③ 실제 Runner G2 → ④ 운영·보안 검증.**

## 0. 통합 범위와 고정 결정

> 이 문서는 S1(`R5.8_S1_Web.md`) 및 S2(`R5.8_S2_Runner.md`)와 함께 읽는다. `packages/contracts`는 세션 3이 소유한 단일 정본이다. 기존 두 문서의 인터페이스를 임의 변경하지 말고, 안전상 불가피한 보완은 **변경 요청 + 계약 버전 테스트**로 전달한다.

**이번 목표 = For Me까지**: Google 로그인 → Workspace/Plan 논리 배정 → 프롬프트로 Channel 생성 → 최초 Run 자동 큐잉 → Docker Runner의 실제 HTML 모션그래픽 Vista 생성 → Validator 통과 → 안전한 Artifact 등록 → Feed 게시·Player 재생 → 새로고침 후 복원.

**이번 범위에서 제외**: 실제 결제, 공개 Discovery, 사용자별 모델 키 연결(BYOK/G3), Channel 정기 실행(G4), iPhone Duo 레이아웃, 소셜 기능, 영구 전용 VM 자동 프로비저닝. 향후 지원할 수 있도록 데이터 모델과 실행 분리만 해 둔다.

### 0.1 네트워크 토폴로지

```text
Browser (앱 Origin; 세션 쿠키)
  └─ https://<app-domain>/auth/* · /api/*
       └─ Core Worker ── D1 (User, Workspace, Channel, Run, Revision, Feed)
               │         └─ Private R2 (staging · artifacts)
               │
               └── HTTPS 응답만 (Runner로 인바운드 연결 X)

Trusted VPS: Runner Daemon ── outbound HTTPS ──> Core /runner/*
               └─ 격리 job container (Agent, Model, Tools)
               └─ 별도 offline validator container

Browser iframe (sandbox='allow-scripts')
  └─ https://<separate-vista-domain>/v/<short-lived-capability>/index.html
       └─ Vista Gateway Worker (서명·권한·리비전 검증) ── Private R2
```

- **첫 로그인에서 물리 VM을 생성하지 않는다.** D1의 Workspace·Plan·Quota와 R2 key namespace를 논리적으로 배정한다. 작업 발생 시 Runner가 자원을 사용한다.
- Web과 Core의 사용자-facing API는 **동일 Origin**(`/auth`, `/api` 리버스 라우트)으로 배치한다. 별도 도메인 CORS/서드파티 세션 쿠키에 의존하지 않는다.
- **Vista는 앱과 별도 등록 도메인(eTLD+1)을 권장/배포 체크에서 확인**한다. `/v/*`는 Viewer Gateway Worker가 서빙하고 R2 bucket은 공개하지 않는다.
- Worker는 Runner를 호출하지 않는다. **Daemon이 register/claim/heartbeat/files/submit/fail을 outbound HTTPS로 수행한다.** 작업 컨테이너는 Core 토큰을 모른다.
- `READY`가 곧 사용자 For Me에 게시 가능한 상태다. 이번 버전은 READY 처리와 FeedEntry 생성을 같은 DB 커밋으로 묶는다. 미래에는 READY와 명시적 `PUBLISHED`를 분리할 수 있지만, **S1·S2 상태 enum을 지금 변경하지 않는다.**

### 0.2 Plan (가설, 프로덕션 요금 확정 아님)

`packages/contracts/profiles.json`이 유일한 정본. S1·S2에 복사·재정의 금지.

| 항목 | free | plus | pro |
|---|---:|---:|---:|
| maxChannels | 1 | 3 | 10 |
| minScheduleIntervalMin | 1440 | 360 | 60 |
| dailyRunCap | 3 | 20 | 60 |
| priority | 1 | 2 | 3 |
| cpus | 1 | 2 | 3 |
| memMb | 2048 | 4096 | 6144 |
| timeoutSec | 300 | 600 | 900 |
| maxRepair | 1 | 2 | 3 |
| browser | false | true | true |

- `cpus/memMb`는 job container **상한**이지 로그인 사용자에게 예약된 호스트 자원이 아니다.
- `browser=false`는 Agent의 웹 브라우징 도구가 등록되지 않는다는 뜻이다. **Vista QA용 독립 Chromium Validator 실행까지 금지하지 않는다.**
- `minScheduleIntervalMin`은 후속 G4 정책용 필드다. 이번 G2에서는 정기 작업을 실제로 켜지 않는다.
- 제공자 모델 비용은 VM 비용과 분리한다. 최초 파일럿에서는 **개발자 관리 OpenRouter 키 + 엄격한 사용 상한**만 사용한다. 이 사실을 사용자 BYOK가 이미 구현된 것처럼 표시하면 안 된다.

## 1. Phase 0 — 독립 세션을 위한 계약 선행 커밋 (최우선)

### 1.1 첫 커밋 산출물

```text
/
├─ package.json                 # workspace scripts 및 공용 devDependencies
├─ pnpm-workspace.yaml
├─ pnpm-lock.yaml
├─ .gitignore · .env.example
├─ .github/workflows/contracts.yml
├─ packages/contracts/
│  ├─ package.json
│  ├─ profiles.json
│  ├─ src/index.ts
│  ├─ src/common.ts             # IDs, errors, pagination, date, plan
│  ├─ src/web.ts                # Web request/response Zod schemas
│  ├─ src/runner.ts             # Runner API + Job + events
│  ├─ src/vista.ts              # Manifest v1, FeedItem, Player messages
│  └─ fixtures/                 # login/me/channels/runs/feed/vista/job/error
├─ services/core/              # Worker 스캐폴드 · 이후 단계 구현
└─ ops/                        # deploy/runbook/VM firewall
```

- 기존 저장소에 루트 `AGENTS.md`, package manager, lockfile, CI가 이미 있으면 **읽고 존중**한다. 새로 만든다는 이유로 기존 설정을 덮어쓰지 않는다.
- `@campsite/contracts`는 Web/Worker에서 import 가능한 **TypeScript + Zod ESM package**로 만든다. Python Runner는 `contracts`에서 export한 **버전 고정 JSON Schema/fixtures**로 검증한다. Runner에게 TS runtime을 강제하지 않는다.
- fixture에는 `empty user`, `one channel pending`, `ready feed`, `failed run`, `CHANNEL_LIMIT`, `RUN_LIMIT`, `stub job`, `manifest fixture`를 최소 포함한다.
- CI `contracts.yml`: Zod schema 테스트, fixture parse, 타입체크, JSON Schema export, OpenAPI/endpoint 계약 정합성 체크. **실패하면 다른 세션 병합 금지.**
- 두 세션이 다른 Git worktree에 있다면 이 첫 계약 커밋을 각 작업 브랜치에 **cherry-pick/merge**해서 공유한다. 파일이 같은 컴퓨터에 있다는 사실만으로 브랜치 간 contracts가 공유되지는 않는다.

### 1.2 API 스펙 — S1과 정확히 일치시킬 사용자 API

| Method | Path | 요청 | 성공 | 비고 |
|---|---|---|---|---|
| GET | `/auth/google/start` | — | 302 Google | state/PKCE/nonce |
| GET | `/auth/google/callback` | code/state | 302 app | 서버 측 OIDC 검증 |
| POST | `/auth/logout` | — | 204 | 세션 폐기 |
| GET | `/api/me` | — | `{user,plan,usage}` | 미인증 401 |
| GET | `/api/channels` | — | `{items:[...]}` | 사용자 소유만 |
| POST | `/api/channels` | `{brief}`, `Idempotency-Key` | 201 `{channelId,runId}` | 최초 Run 자동 생성 |
| POST | `/api/runs` | `{channelId,prompt}` | 202 `{runId}` | 소유권·한도 검사 |
| GET | `/api/runs/:id` | — | `{status,phase,vistaId?,error?}` | 본인 소유 |
| GET | `/api/feed?cursor` | — | `{items,nextCursor}` | For Me 최신순 |
| GET | `/api/vistas/:id` | — | `{vistaId,title,summary,aspect,playUrl,posterUrl,expiresAt}` | URL 재발급 |

- S1에서 정확히 지정하지 않은 채널 응답을 다음처럼 고정한다: `Channel = {id,title,brief,createdAt,latestVistaId?:string|null,latestPosterUrl?:string|null}`; `GET /api/channels → {items:Channel[]}`. **채널 레일은 latestPosterUrl을 사용**한다. 초기에는 `null`.
- 사용자 `POST /api/channels`의 최초 Run은 **해당 brief를 prompt로 사용**한다. `title`은 brief 첫 문장의 안전한 축약값으로 초기에 만들 수 있으나, 콘텐츠 자체를 자동으로 바꾸지 않는다.
- `POST /api/runs`에도 가능하면 `Idempotency-Key`를 받는다. 필수 헤더는 최초 채널 생성에만 적용해 S1 계약을 깨지 않는다.
- `GET /api/feed?cursor`의 `FeedItem = {vistaId,channelId,channelTitle,title,summary,posterUrl,aspect,createdAt}`; `nextCursor`는 문자열 또는 `null`. `createdAt` ISO8601 UTC 문자열. `aspect`는 `"9:16" | "free"`.
- 모든 사용자 API의 오류는 `{error:{code}}`만 노출한다. 허용 코드: `UNAUTHENTICATED`, `CHANNEL_LIMIT`, `RUN_LIMIT`, `NOT_FOUND`, `INVALID_REQUEST`, `RUN_FAILED`. 내부 SQL/모델/API 키/스택은 반환하지 않는다.
- 프론트엔드 copy 정책은 S1 소유다. Core가 UI 문구나 기술 사양을 사용자 화면에 강요하지 않는다.

### 1.3 API 스펙 — S2와 정확히 일치시킬 Runner API

모든 요청: `Authorization: Bearer <NODE_TOKEN>` (노드별로 발급·회전 가능). Runner 인증은 사용자 세션과 분리한다.

| Method | Path | 요청 | 성공/오류 |
|---|---|---|---|
| POST | `/runner/register` | `{nodeId,hostCpus,hostMemMb,version}` | 200 노드 등록 확인 |
| POST | `/runner/claim` | `{nodeId,freeMemMb,freeCpus}` | 200 Job 또는 204 |
| POST | `/runner/runs/:id/heartbeat` | `{phase}` | 200 `{leaseUntil,cancel:boolean}` |
| PUT | `/runner/runs/:id/files/<path>` | raw bytes + `x-sha256` | 2xx staged |
| POST | `/runner/runs/:id/submit` | `{manifest,usage:{tokensIn,tokensOut,durationMs}}` | 201 `{revisionId}` / 422 `{errors[]}` |
| POST | `/runner/runs/:id/fail` | `{code,retryable}` | 200 처리 상태 |

```jsonc
// claim 200 응답 (정본)
{
  "runId": "r_...", "channelId": "ch_...", "attempt": 1,
  "prompt": "이번 요청", "channelBrief": "채널 지침",
  "recent": [{"title":"…","summary":"…"}],
  "profile": "free",
  "limits": {"cpus":1,"memMb":2048,"timeoutSec":300,"maxRepair":1,"browser":false},
  "model": {"provider":"openrouter","modelId":"…","apiKey":"…"},
  "artifactVersion": "1"
}
```

- `recent`: 같은 채널의 **READY Vista 최대 3개**, 최신순. 해당 사용자/채널 외의 정보 혼입 금지.
- Job 안의 `model.apiKey`는 파일럿에서만 Core→신뢰된 Daemon으로 전달한다. 로그/DB/트레이스/fixture/실제 artifact에 쓰지 않는다. Daemon은 작업 컨테이너의 **환경변수에만** 넣는다.
- Run 실패 코드: `MODEL_ERROR`, `TIMEOUT`, `VALIDATION_FAILED`, `TOOL_ERROR`, `OOM`, `CANCELED`.
- **안전 필수 계약 보완 요청(S2에 즉시 전달)**: claim 결과의 기존 `attempt`를 이후 heartbeat/files/submit/fail 요청의 `X-Run-Attempt` 헤더로 함께 보내도록 한다. Core는 `nodeId + attempt + 현재 lease 유효성`을 검증한다. **기존 요청 본문·성공 응답 형식은 변경하지 않는다.** 이는 만료된 실행이 새 시도의 결과를 덮어쓰는 race를 막는 fencing이다. 정본 스키마에 헤더를 명시하고 S2 변경 요청 항목으로 기록한다.

### 1.4 Vista Manifest v1 / Player 프로토콜

```jsonc
{
  "schema": 1,
  "title": "…", "summary": "한두 문장",
  "entry": "index.html", "poster": "poster.png",
  "aspect": "9:16", "durationHintMs": 30000,
  "files": [
    {"path":"index.html","sha256":"<64 lowercase hex>","bytes":12345},
    {"path":"poster.png","sha256":"<64 lowercase hex>","bytes":23456}
  ],
  "generator": {"runId":"r_...","modelId":"…"}
}
```

- `aspect`: `"9:16" | "free"`. 파일 **최대 12개**, 총합 **최대 3MB**, 경로 정규식 `^[a-z0-9._-]+(/[a-z0-9._-]+)*$`, 허용 확장자 `html css js json png jpg webp svg woff2`. 외부 네트워크 요청 금지.
- 모든 참조 파일(특히 `entry`, `poster`, 별도 `campsite-vista.js` shim)이 `files[]`에 있고, 중복 경로/누락/미선언 추가 파일이 없는지 검증한다. **S1·S2 문서의 Manifest는 축약 예시일 뿐 poster 누락을 허용한다는 뜻이 아니다.**
- 호스트→Vista: `campsite:play | campsite:pause | campsite:restart`; Vista→호스트: `campsite:ready` (`durationMs?`). 3초 내 ready가 없으면 iframe load fallback. S2가 shim을 소유하며 Core는 인위적으로 iframe 내부를 수정하지 않는다.
- iframe sandbox에 `allow-scripts`만 허용하므로 Vista의 브라우저 Origin은 보통 `null`(opaque origin)이다. Web의 수신 측은 `event.source === iframe.contentWindow`와 허용 type/payload로 검증해야 하며 **`event.origin === Vista 도메인`을 요구하면 안 된다**. 부모→iframe의 초기 메시지는 opaque origin 특성상 `targetOrigin='*'`가 필요할 수 있으므로 **절대 키·세션·민감 정보를 메시지에 넣지 않는다**. Web 구현은 S1 소유.

## 2. Phase 1 — Google 인증 + Workspace + D1

### 2.1 OAuth 및 세션

- Google OpenID Connect Authorization Code + PKCE, `state`, `nonce`를 검증한다. `iss`, `aud`, `exp`, 서명(JWKS), `email_verified` 등 ID token 필드 검증을 통과한 사용자만 생성한다.
- ID는 Google `sub`를 안정적인 외부 식별자로 사용한다. 이메일 변경은 동일 사용자를 새로 만들지 않는다.
- 서버 측에서 랜덤 opaque 세션 ID 발급, DB에는 **해시**만 저장한다. 쿠키 `HttpOnly; Secure; SameSite=Lax; Path=/`. 운영 환경 HTTPS 강제, 로그아웃 시 DB 세션 폐기.
- 로그인 직후 `users`, `workspaces`, `entitlements`를 idempotent하게 upsert한다. 두 탭에서 동시 로그인해도 **Workspace 1개**.
- 상태를 바꾸는 `/api/*` POST에는 Origin 검사 + CSRF 방어를 적용한다. Runner Bearer 인증 경로와 구분한다.
- 인증 계정이 곧 실행 인프라의 SSH/Docker 권한을 의미하지 않는다.

### 2.2 D1 Migration (필수 엔티티)

`services/core/migrations/0001_init.sql`과 후속 migration을 만든다. SQL은 SQLite/D1 문법에 맞고 모든 인덱스/제약을 명시한다.

| 테이블 | 최소 필드 | 불변식 |
|---|---|---|
| `users` | `id,google_sub,email,name,avatar_url,created_at` | `UNIQUE(google_sub)` |
| `sessions` | `id_hash,user_id,expires_at,revoked_at` | 만료·철회 검사 |
| `workspaces` | `id,user_id,r2_prefix,created_at` | `UNIQUE(user_id)` |
| `entitlements` | `workspace_id,plan,updated_at` | `plan in free/plus/pro` |
| `channels` | `id,workspace_id,title,brief,created_at` | 소유권 + 채널 한도 |
| `runs` | `id,workspace_id,channel_id,prompt,status,phase,attempt,priority,node_id,lease_until,cancel_requested,created_at,updated_at` | 허용 상태 전이·단일 소유 |
| `runner_nodes` | `id,token_hash,version,last_seen_at,host_cpus,host_mem_mb` | nodeId와 Bearer binding |
| `staged_files` | `run_id,attempt,path,sha256,bytes,r2_key` | UNIQUE(run,attempt,path) |
| `vistas` | `id,workspace_id,channel_id,latest_revision_id,created_at` | 사용자 소유 |
| `revisions` | `id,vista_id,run_id,manifest_json,artifact_prefix,created_at` | artifact 불변 / `UNIQUE(run_id)` |
| `feed_entries` | `id,workspace_id,channel_id,vista_id,revision_id,created_at` | 단일 READY Run 중복 게시 금지 |
| `quota_usage` | `workspace_id,usage_date,run_count` | 원자적 일별 제한, UTC date |
| `idempotency_keys` | `workspace_id,scope,key,request_hash,response_json,created_at` | 동일 키·동일 요청만 재사용 |

추가 요구:
- 날짜는 저장·API에서 UTC. `created_at + id` 복합 커서로 안정적인 피드 페이지네이션 구현.
- `channels(workspace_id,created_at)`, `runs(status,priority,created_at)`, `runs(node_id,lease_until)`, `feed_entries(workspace_id,created_at,id)` 인덱스.
- 사용자 소유권은 **모든 단일 리소스 조회에서도** workspace join으로 확인한다. 타인 ID에 대해서는 정보 노출 없는 `NOT_FOUND` 반환.
- D1+R2를 하나의 ACID 트랜잭션이라고 가정하지 않는다. R2는 단계별 저장 후 최종 D1 메타데이터 커밋으로 노출을 제어한다.

### 2.3 동시성에 안전한 Channel·Run 한도

- `POST /api/channels {brief}`에서 brief 정규화·길이검사 → 인증 → `Idempotency-Key` 검사 → 한도 확인 → 채널과 최초 Run을 원자적으로 생성한다.
- 채널 한도 체크와 INSERT를 **서로 다른 비보호 read/insert 경로로 구현 금지**. D1 트랜잭션/조건부 SQL/고유키를 조합해 두 요청 동시 호출에서도 초과하지 않음을 증명한다.
- `POST /api/runs`는 본인 Channel만 허용. UTC 기준 `dailyRunCap`을 원자적으로 차감한다. 초과 실패 시 잔여 Run/Channel 레코드가 남으면 안 된다. 실패한 Run의 환급 정책은 파일럿에서 **명확히 문서화**한다(권장: 의도적으로 생성된 Run은 재시도 횟수와 별도로 1회 과금 계수; 인프라 장애는 환급).
- `Idempotency-Key`가 같고 body hash가 동일하면 **동일 channelId/runId**를 반환한다. 키가 같고 body가 다르면 `INVALID_REQUEST`; 24시간 만료 등 보존 정책은 운영 설정에서 통일한다.

## 3. Phase 2 — Runner Queue + Lease (G1 준비)

### 3.1 Node 등록과 claim

- `NODE_TOKEN`은 노드별로 발급하고 Core에는 해시 저장. 인증 시 요청 토큰에서 nodeId를 식별하고 제출된 body.nodeId와 일치 여부 확인. 허용된 노드만 register/claim.
- 요청 `freeMemMb,freeCpus`는 후보 필터이지만 **호스트 자원 보안 경계는 VPS Daemon/cgroup**이다. Core가 클라이언트의 자원 숫자를 절대 신뢰하지 않는다.
- `POST /runner/claim`: `QUEUED` 중 `limits.memMb <= freeMemMb`, `limits.cpus <= freeCpus`를 만족하는 Run을 priority DESC, createdAt ASC로 **조건부 단일 SQL UPDATE ... RETURNING** 방식으로 선택·CLAIMED 갱신한다. 후보가 없으면 204.
- `attempt=1`이 최초 실행. Lease 만료로 재큐잉할 때 `attempt+1` (전체 최대 2회 시도). **동일 Run의 성공 Revision은 정확히 1개**.
- claim이 동시에 2개 와도 1개만 소유하도록 통합 테스트를 만든다. D1 지원 SQL/동작을 실제 테스트 환경에서 확인하고, 단순 SELECT→UPDATE 분리로 퇴행시키지 않는다.

### 3.2 Run State Machine

```text
QUEUED ──claim──> CLAIMED ──heartbeat / start──> RUNNING
  ▲                    │                          │
  │                    └──timeout/fail─────────────┤
  └──lease expired (attempt < 2)                   ▼
                                            VALIDATING
                                                 │
                               validated+committed → READY → FeedEntry
                               terminal/error     → FAILED

RUNNING/CLAIMED/VALIDATING -- cancel requested --> CANCELED (실패 코드)
```

- **status enum은 S1/S2 고정 6개**: `QUEUED,CLAIMED,RUNNING,VALIDATING,READY,FAILED`. `CANCELED`는 status가 아니라 내부 `failCode`이다.
- **phase enum은 S1/S2 고정 5개**: `QUEUED,SEARCHING,DRAFTING,VERIFYING,DONE`. `heartbeat.phase=VERIFYING` 시 status VALIDATING으로 전이 가능. Phase DONE은 READY 처리 후 UI에 나타난다.
- heartbeat 30초, Lease 기본 90초 권장(구성값). timeout은 Plan의 `timeoutSec`; Lease 갱신과 **전체 작업 실행 시간 제한**은 별개다.
- 만료 재큐잉은 Core의 보상 작업(요청 시 + 운영 Cron stub의 housekeeping 경로)으로 처리한다. 정기 Channel 발행 G4와 구분한다.
- `X-Run-Attempt`, node binding, 유효 lease와 허용된 상태를 검사하여 이전 시도의 submit/files/heartbeat를 **409 또는 403으로 거절**한다.
- `fail {retryable:true}`라 해도 전체 시도 한도를 초과하면 FAILED. `CANCELED`은 재큐잉하지 않는다.
- `register`·`claim`·`heartbeat`·`submit`은 무해하게 여러 번 호출되어도 잘못된 상태 변경·중복 발행이 생기지 않도록 한다.

### 3.3 G1: 고정 HTML로 처음부터 끝까지 배관 통과

1. Google 로그인 /api/me → Workspace/Plan 정상.
2. 새 Channel 생성 → idempotency 확인 → Run QUEUED 생성.
3. S2의 `--stub` Runner가 outbound register/claim/heartbeat를 수행.
4. `index.html`, `poster.png`, `manifest.json`을 생성·검증하고 파일별 PUT/submit.
5. Core가 READY Revision 생성 + FeedEntry 커밋.
6. S1 For Me에 feed item 표시, iframe 안전하게 재생.
7. 새로고침·브라우저 재접속 후에도 동일 Vista가 유지됨.

**G1은 LLM 품질 검증이 아니다.** 운영 배관과 안전한 게시의 성공을 의미한다.

## 4. Phase 3 — R2 Artifact Commit + 별도 Origin Player

### 4.1 Staging과 원자적 게시

- R2는 **private**. 공개 `r2.dev` 및 무인증 custom domain 접근 금지.
- staging key: `staging/<runId>/<attempt>/<validatedPath>`; immutable artifact key: `artifacts/<workspaceId>/<channelId>/<vistaId>/<revisionId>/<path>`.
- 파일 PUT마다 소유 node/attempt/lease를 확인 → 경로 정규화 → bytes/sha256 계산·`x-sha256` 대조 → staged file metadata 저장. 업로드는 manifest 검증 전이라도 **전체 3MB·파일 수 한도**를 누적 집행한다.
- `submit` 검증: current run/attempt, staged 파일 완비, `entry`/`poster` 실제 존재, Manifest Zod/JSON Schema, 선언 크기/sha256 일치, 확장자·경로, `generator.runId` 동일, 동일 run 기존 Revision 여부. S2 validator의 브라우저 QA 증거도 별도 수집·기록할 수 있지만 Core는 Runner 검증을 **독립적인 신뢰 경계로 과신하지 않는다**.
- staging 파일을 **불변 revision prefix에 완전히 복사/확인한 다음** D1에서 `(vista,revision,feed_entry,run READY)`를 한 번에 commit. 복사 중 실패하면 Feed에는 나타나지 않아야 한다.
- 동일 run의 submit 재시도는 기존 `revisionId`를 그대로 반환. `UNIQUE(run_id)` 및 `UNIQUE(feed_entries.revision_id)`를 DB로 강제한다.
- 장애로 남은 staging/orphan immutable object는 TTL 기반 GC에서 정리한다. **DB에 게시된 revision 파일은 GC 금지.**
- `usage.tokensIn/Out`은 Runner가 보고한 **관측값**이며 과금 증빙으로 무검증 신뢰하지 않는다. 파일럿 비용은 별도로 공급자 사용량과 대조한다.

### 4.2 Manifest 파일을 상대 경로로 안전하게 제공

`GET /api/vistas/:id`는 사용자 인증·소유권을 확인한 후 `playUrl, posterUrl, expiresAt`을 발급한다. Vista Gateway는 다음 규칙을 따른다.

- 권장 URL 패턴: `https://<vista-domain>/v/<signed-capability>/index.html` 및 같은 prefix의 상대 파일 (`./style.css`, `./campsite-vista.js`, `./poster.png`). **index.html만 쿼리 서명하고 하위 assets가 403이 되는 설계를 금지**한다.
- capability에는 `vistaId,revisionId,workspaceId,expiresAt,accessVersion` 등을 무결성 보호하여 넣는다. path는 manifest allowlist 안에 있어야 하며 `..`, percent-encoding 경로 우회, 파일 유형 위조를 거절한다.
- 각 요청에서 토큰 만료·현재 revision의 접근 권한/철회 버전을 검증한다. 접근 철회는 **유효한 과거 링크와 캐시에서도 시행**해야 한다. private Vista는 `Cache-Control: private, no-store` 원칙(성능 측정 후 세분화)으로 시작한다.
- CSP: `default-src 'none'`; 필요한 HTML/CSS/JS/img/font에 한해 self/nonce/hash 기반 허용, `connect-src 'none'`, `form-action 'none'`, `base-uri 'none'`, `frame-ancestors`는 앱 Origin으로 한정. **초기 inline HTML/CSS/JS 전략과 CSP를 함께 시험**한다. 정적 문자열 금지 검사만으로 악성 JS·네트워크 접근을 완전히 봉쇄했다고 선언하지 않는다.
- `Content-Type`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`를 설정한다. HTML에 임의 외부 SDK·CDN·원격 폰트를 로드하지 않는다.
- 브라우저에서는 S1의 iframe `sandbox="allow-scripts"`를 유지한다. Vista Gateway가 같은 앱 Origin으로 오인되지 않도록 배포 smoke test에서 검증한다.

### 4.3 피드 정합성

- `GET /api/feed`는 현재 사용자 Workspace의 `feed_entries`만 반환. READY Revision만 노출하고, READY 이전 staging 또는 실패한 Run은 보이지 않는다.
- 채널 레일의 최신 poster는 같은 Workspace의 최신 READY Vista에서 계산한다.
- `GET /api/vistas/:id`는 접근이 차단/삭제/비공개 전환되면 기존 링크를 무효화하고 404를 반환한다. 이미 받은 자산을 사용자 브라우저 메모리에서 원격 삭제할 수 있다고 주장하지 않는다.
- Vista Player의 재생·정지·재시작은 Artifact의 장기 저장/복구와 별도 관심사다. 이번 G2는 **저장된 피드 항목·revision 재진입**을 보장하며, Vista 내부의 임의 조작 상태를 장기 저장하는 범용 시스템은 후속 범위로 둔다.

## 5. Phase 4 — Integration Gate G2 (실제 생성)

### 5.1 통합 순서

1. `packages/contracts` CI 녹색 및 S1/S2 양쪽 브랜치에 동일 버전 반영.

7. 사용자가 아닌 제3자 계정으로 동일 Vista/Channel 접근 실패.

## 6. Phase 5 — 운영 보안·배포 Runbook

### 6.1 Cloudflare

- `services/core/wrangler.toml|jsonc`: Worker routes, D1 binding, private R2 binding, 환경별 secrets. 실제 키·도메인 소유정보·OAuth secret을 Git에 커밋하지 않는다.
- Core user API와 Vista Gateway는 **분리된 Worker entrypoint/route**로 구성할 수 있다. 정책 공유 코드가 필요하면 Core 내부 모듈로 재사용한다.
- Google OAuth redirect URI는 배포 주소와 정확히 일치. HTTPS/cookie 정상 여부 확인.
- R2 private bucket, bucket public development URL 비활성화, Cache/CSP 검사.
- Secret rotation: `GOOGLE_CLIENT_SECRET`, `SESSION_SECRET`, `VISTA_SIGNING_SECRET`, `NODE_TOKEN`, 파일럿 OpenRouter 키의 교체·폐기 절차 작성.

### 6.2 VPS/Runner Node

- VPS SSH는 키 기반, 최소 운영 사용자. Docker Daemon 접근 권한 제한. Runner는 outbound HTTPS만; 외부 인바운드 앱 포트 미개방.
- Job 컨테이너 비루트, 자원 cgroup 제한, 읽기전용 rootfs, 도구별 outbound allowlist, private IP/link-local/metadata 접근 차단. **네트워크 이름만으로 SSRF 방어가 되는 것은 아니다.**
- Validator는 `--network none`. `--no-sandbox`가 불가피한 Chromium은 보강된 컨테이너 격리 근거를 남기고 별도 리스크로 표기.
- `ops/vps-setup.md`, `ops/network-policy.md`, `ops/incident-response.md`, `ops/cost-monitoring.md`, `ops/deploy.md` 작성. 설정 적용과 침투 테스트를 별도 DoD로 검증한다.
- 파일럿 키에 공급자 일일/월간 지출 상한 및 이상 사용 탐지. 무료 Plan에도 무제한 유료 토큰을 허용하지 않는다.

### 6.3 Scheduler (향후 G4, 이번에 **실행 금지**)

- Cron Trigger 소유는 Core 단독. 각 사용자 Channel을 Cloudflare 배포 Cron 목록에 개별 등록하지 않는다.
- G4 설계 자리만 확보: 중앙 `scheduled()` → 마감된 Channel 조회 → idempotent Run 큐잉. **이번 G2에서 자동 Channel 재실행은 켜지 않는다.**
- 단, lease 만료 정리·orphan staging 정리 같은 housekeeping은 선택적으로 내부 scheduled handler에서 할 수 있으며 **사용자 Channel Cron과 분리된 기능**임을 문서화한다.

## 7. 세션 간 커뮤니케이션/Worktree 운영

- 세션 3이 **가장 먼저 contracts의 첫 커밋 해시**를 공유한다. S1과 S2는 각각 자기 worktree/브랜치에서 작업하며, 이 커밋을 기준으로 mock과 job을 붙인다.
- S1에게 전달: `Channel`, `FeedItem`, `GET /api/channels`, Zod fixtures, UI에서 보일 수 있는 에러 코드, `playUrl`의 경로·만료 방식.
- S2에게 전달: `Job`, Manifest, file upload, 상태 전이, `X-Run-Attempt` fencing 헤더 추가, claim의 모델 키 취급, G1 `--stub` 테스트 계정.
- 서로의 폴더에 직접 수정 커밋하지 않는다. 계약 수정 요청은 `ops/contract-change-requests.md`에 이유·변경 전후·하위 호환성·테스트를 기록하고 세션 3만 정본을 갱신한다.
- 통합 브랜치에서는 **contracts → Core → Runner stub → Web mock → real Runner** 순서로 병합한다. 충돌을 무조건 ours/theirs로 덮지 않는다.
- S1·S2가 요구한 컴포넌트/운영 UI는 추가하지 않는다. 프론트엔드 UI 결정은 S1의 기존 디자인 요구를 따른다.

5. **차기 작업**: 어떤 세션이 어떤 커밋을 받아야 하고 어떤 통합 게이트가 남았는가.

## 9. 첫 작업 (다른 세션의 진행을 막지 않도록 즉시)

1. 두 지시문과 저장소 `AGENTS.md`/기존 파일을 읽고 **5줄 작업 계획**을 보고한다.
2. 모노레포 뼈대와 `packages/contracts`의 **모든 endpoint schema + profiles + fixture + 타입 테스트**부터 구현한다.
3. **첫 커밋과 contracts 버전/해시를 즉시 S1·S2에 전달**한다. 이 단계 전에는 Core DB를 오래 파지 않는다.
4. Core Worker/D1 migration과 `/api/me`, `/api/channels`, `/api/runs`·Runner stub queue를 만든다.
5. **G1 고정 HTML 배관 통과 → G2 실제 생성/Player 검증** 순으로 실행한다.
